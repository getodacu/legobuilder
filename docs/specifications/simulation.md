# Post-assembly simulation

Status: the shared deterministic kinematics module and behavioral unit fixtures are implemented; this document does not claim those checks have been exercised. Research has not established calibrated physical models or completed all robot reconstructions. All four LEGO source-specific scenarios remain acceptance goals. Historical VEX research is outside simulation and delivery scope. Sources: [fidelity ceiling](../research/fidelity-requirements.md#simulation-fidelity-ceiling), [source register](../research/robot-sources.md), and each linked model research note.

## One hierarchy, deterministic kinematics

`src/lib/simulation/kinematics.ts` is a deep module importing shared model types, not Three.js or Svelte. It consumes the same `RobotModel` part/subassembly hierarchy, connections, joints, internal motor nodes and completed assembly pose. No second simplified robot viewer, generic simulation replacement or independent copy of the BOM is allowed. Prepared motors stay one inventory unit even when a verified internal rotor mesh moves. Loose sample objects are the same declared sample subassemblies, not duplicated robot components.

```ts
compileSimulation(assembly: CompiledAssembly, scenario: SimulationScenario): CompiledSimulation
createSimulationFrame(compiled: CompiledSimulation): SimulationFrame
sampleSimulation(compiled: CompiledSimulation, timeMs: number, out: SimulationFrame): SimulationFrame
```

The UI enables entry only after all supported robot assembly steps have completed and the selected scenario's prerequisites are satisfied; incomplete source coverage remains visible and cannot be called whole-model completion. Sampling accepts finite times, clamps to scenario endpoints and mutates a preallocated frame, overwriting all lanes. `SimulationFrame.assembly` contains the same indexed part transforms/flags consumed by the renderer; installed counts remain the completed assembly's counts. Joint values follow `CompiledSimulation.jointIds`; sensor values follow `sensorPartIds` and hold the most recent time-ordered signal, or null before a signal. Multiple channel displays can read the compiled scenario's typed signals; a light value must not masquerade as a distance measurement.
The nested `assembly.timeMs` remains the completed assembly duration, with its final step index and installation/connection flags; `SimulationFrame.timeMs` is the independent scenario time. Simulation overwrites derived pose/internal-node buffers and joint/sensor values only, so a renderer/UI cannot accidentally show partially assembled counts when scenario time restarts at zero. Object-event transforms are parent-local for attachment and world-space when released to a null parent; `rootMotion` keyframes identify their target node explicitly and use world-space transforms.


Use scenario time, never wall clock or accumulated frame delta. Position commands interpolate absolute joint coordinates; speed commands integrate their explicit start/end speeds analytically from the declared command start. Gaps hold the last endpoint, initially the declared joint zero. Reject overlapping commands on one coordinate, incompatible units, nonfinite values, unsupported unassigned motor bindings and unsatisfied loop constraints. Reset samples time zero and resets the UI's command log; pause/resume and backward/random seek use the same sampler. Interactive controls record timestamped commands/inputs in an immutable scenario log; compile an updated log on input changes, not each animation frame. Replaying the same input log at the same time reproduces the same output. No hidden timer callback or key-held accumulator mutates the scene.

## Joints, linkage constraints and motors

The initial rigid parent graph is supplied by subassemblies; joints own movable child roots in that graph. For a joint, `origin` is its parent-local joint frame and `childTransform` is the fixed transform from joint motion frame to child origin at zero. Evaluate `Tchild = Tparent × Torigin × M(q-zero) × TchildTransform`, where `M` is identity for fixed, rotation around the normalized joint-local axis for revolute, or translation along it for prismatic. Revolute coordinates and speeds use radians/radians per second; prismatic coordinates use mm/mm per second. Fixed joints ignore axis/zero and do not accept drive commands. Do not add a prismatic joint merely because a rotary linkage's endpoint rises.

A child has one structural parent/joint; closed loops are additional `LinkageConstraint` records, not cycles in the transform tree. A planar closed-loop solver uses evidence-backed local anchors/link lengths, driver coordinate and an authored reference branch to derive dependent revolute coordinates. Select the branch deterministically from the reference configuration and analytic path, not the previously rendered frame; reject unreachable/singular input ranges before playback. Residual must stay within the declared tolerance. A fixed ratio coupling is appropriate only for a verified gear/shaft relation, not a substitute for a nonlinear four-bar mechanism. The Hand and Sorter require solved passive linkage motion with the real parts, not jaw/fork translation cheats.

Motor commands carry evidence distinct from joint geometry. Port-to-physical-axis assignment must be verified or openly left unbound; Quality Check A/F are known motor ports but not verified yaw/pitch identities. Keep source encoder-degree values, shortest-path semantics and source power/speed units in original summaries/evidence; convert them into explicit radian-based authored tracks with documented zero/sign/transmission mapping. Percentage power, degrees per second and mechanical output angle are not interchangeable. A source command's 0/240/25 target is not a physical joint stop.

Every limit is explicitly `basis: modeled` or `physical`; modeled operating bounds are conservative app ranges, not vendor specifications. Source-unverified limits, max speed, cable travel, grasp aperture, payload and force must never be presented as physical. Unknown physical limits stay unknown even if modeled bounds permit a safe-looking visualization. Validate scenario commands against modeled bounds, show a useful error instead of silently clamping away required behavior. No physical limit is accepted without source/measurement evidence. If a required range cannot be justified even as an explicit model assumption, block that scenario while keeping its acceptance requirement open.

Optional `internalBinding` selects an actual asset node and its moving side. The Quality Check upper motor is mounted through its output while its body carries the sensor: do not fix both motor bodies to the base. Motor internals must not be articulated without a genuine separated rotor/body node or evidence-backed component decomposition. Missing separation is an asset prerequisite, not permission to spin the entire device incorrectly.

## Drive, object and sensor behavior

For a differential drive with evidence-tagged wheel radius `r` and track `b`, derive planar body motion from left/right wheel travel: `v = r(ωL+ωR)/2`, `yawRate = r(ωR-ωL)/b`. Use a declared positive-forward convention and exact straight/constant-curvature integration over command segments; variable-speed segments need deterministic analytic integration or fixed compile-time numerical integration independent of render frames. The derived root motion drives the real assembled hierarchy and agrees with wheel rotation. `differentialDrive` parameters are evidence-tagged assumptions until calibrated; mutually exclude a simultaneous hand-authored `rootMotion` track for that root. A rootMotion track for scripted sample presentation is an app-authored path, not inferred wheel dynamics.

Simple object interaction uses explicit attach/release events and local/world transforms. At an event, verify the geometric capture condition for the modeled jaw/fork region; an accepted attach moves the existing object subtree with its holder until release. Sampling reconstructs this parentage from the log at any time. The release pose and subsequent modeled support/path are explicit; never let a source package teleport from pedestal to fork without a visible coherent trajectory. These are kinematic support assumptions, not validated friction, impact, grip force or load stability. Hand hold must keep the object consistently constrained between the coupled jaws; Sorter fork support and drop must respect actual object/fixture geometry. Add a physics engine only if required behavior truly needs collision dynamics, with independently justified parameters and deterministic replay requirements intact.

Signals declare `scripted-input`, `geometric-model` or `documented-output`. A color input can be a user-selected test event or a geometry/color-region approximation, not a claim of spectral simulation. A distance reading requires a declared geometric range model; it is not needed to invent a distance-triggered Quality Check program. Device light output and input sensor measurements remain distinct. Captive cable paths belong to their devices and do not increase prepared-unit inventory. Route control points are parent-local; recompute through the same articulation hierarchy. Connection/wiring evidence, visually inferred route, physical length, clearance and cable-safe travel are separate claims. Unknown cable routing cannot establish a physical travel limit.

## Implemented engine contract and numerical ceilings

- Compilation samples the existing assembly engine at its completed duration and consumes its packed world-space part/subassembly buffers. Final assembly parent changes are replayed chronologically; joint children replace only their actual hierarchy edge. Joint zero poses must agree with the completed assembly, and structural/coupling/loop dependency cycles are rejected. No staging pose is reused as a completed joint frame.
- Commands are copied into an immutable replay log. Linear/smoothstep position polynomials and the exact integrals of linear/smoothstep speed polynomials produce absolute coordinates; gaps hold the preceding endpoint. A new position track must start at that held coordinate. Units, overlapping intervals, extrema (including speed reversals), classified bounds and commanded/coupled peak speeds are checked at compilation. Unknown motor-to-axis assignments cannot accept commands. Physical limits/speeds require documented or measurement evidence; modeled bounds remain app operating ranges.
- Planar distance-anchor closure is solved with finite-difference Newton/Gauss–Newton updates and pivoted elimination, not a transmission ratio. `referenceJointValues` has exactly the order `[driverJointId, ...dependentJointIds]`; coordinates use the corresponding joints' absolute radian coordinates. Reference closure, coplanarity, parallel revolute axes, dependent ownership and rank are validated. A compile-time reference-continuation atlas spans the commanded driver range plus reference, at intervals no larger than 0.005 rad and at most 8192 intervals. Endpoints and three interior points per interval must solve. Every sample starts from its atlas interpolation, then solves again to at most `min(toleranceMm * 0.01, 1e-8)` residual; no prior rendered frame is used. This finite atlas is not a proof of reachability at every real coordinate: any unsolved/singular sample still fails before output mutation. Evidence-backed nonsingular operating ranges remain an authoring prerequisite, especially near toggles.
- Several driven loops may share one powered axis: before compiling each later branch atlas, solve preceding loops from their own deterministic atlases at the same driver coordinate. The same ordered solver runs on random seeks, so a downstream anchor never sees a predecessor frozen at its zero pose. `tests/unit/kinematics.test.ts` independently checks both closed-link distances at forward, reverse and random timestamps.
- Motor `internalBinding.geometryNodeId` selects the real separated rotor node. For `movingSide: rotor`, the motor body remains on its fixed hierarchy edge while the rotor follows the joint pivot. For `movingSide: body`, the body and its attached hardware move through the real child edge; the rotor countertransforms in the motor-local internal-node buffer, staying fixed relative to the joint parent. Nested internal asset nodes retain parent-local transforms. No additional motor inventory unit or anonymous replacement mesh is created.
- Driving uses **negative local Z forward, Y up**, with both positive wheel coordinates rotating about root-local **negative X**. Wheel origins must have equal height/longitudinal position, left X less than right X, and a lateral separation equal to the declared track. Required `differentialDrive.axleCenterInRoot` must equal their actual root-local midpoint. `initialTransform` remains the initial **root**, not axle, pose. Integration moves the axle frame and conjugates through the root-to-axle offset, so a front-corner assembly origin does not become the turn center. The root must be free, own the real wheel descendants and have no simultaneous `rootMotion`.
- Straight/reverse and proportional wheel-speed/constant-curvature intervals use their exact wheel-angle travel and circular arc. Other intervals use five-point Gauss–Legendre quadrature on a fixed compile-time grid no wider than 1 ms, also split at command boundaries; only the final partial cell is recomputed on seek. Grid storage is capped at 200000 intervals (at most 200 s); oversize logs fail helpfully rather than changing accuracy silently. Quadrature is deterministic and high-order, **not a certified millimeter error bound**: error depends on authored speed/yaw rates and must be checked against a scenario's tolerance. No physical slip, tyre deformation or collision force is modeled.
- Object events operate on existing nonempty sample subassemblies or optional `RobotModel.simulationObjects` IDs, never robot-BOM roots. Props resolve real geometry/material metadata and use `AssemblyFrame.environmentTransforms`/`environmentVisible`, indexed by `CompiledAssembly.simulationObjectIds`; assembly playback resets their initial transforms and hides them, simulation shows them without recounting parts. Attach/release requires at least two distinct holder-local/object-local contact pairs, a finite maximum gap and explicit translation/angular continuity tolerances. Holder contacts must belong to the actual receiving/holding subtree. Both current and proposed event poses must satisfy contact gaps. Attach records holder-local pose; release records world pose and can continue a root-motion support path with a matching release keyframe. This validates declared contact geometry, not mesh collision, force or friction.
- Sensors hold their latest signal or null before the first event. Device order follows model part order: input sensors, plus controllers explicitly emitting documented light output. One held lane per device is intentional; typed source signals remain in the immutable log for separate input/output channel displays. Duplicate timestamps on one lane are rejected instead of choosing an ambiguous winner.
- A frame and every output buffer belong to exactly one compilation. Finite-time, identity, lane length and foreign-frame checks precede writes. Closure and object capture failures occur on private scratch/at compilation. Sampling reuses all transform/joint/sensor buffers, restores completed assembly counts/flags and keeps assembly time separate from scenario time. There is no Three.js/Svelte dependency or per-sample scene-object allocation.

`tests/unit/kinematics.test.ts` supplies Node `test`/`assert` behavioral fixtures for nonzero joint pivots, output-mounted motor counterrotation, completed reparenting, polynomial commands/couplings/limits, nonlinear reference-branch closure, actual offset-axle driving, independent speed-curve quadrature, two-contact sample/prop capture, release continuity, held events/reset and pre-mutation rejection. These analytic specimens are not source-geometry or completed-robot fit acceptance evidence. Parent integration exercised the unit suite and the four authored source models; the current [coverage ledger](../validation/coverage-baseline.md) separates executable behavior from unverified manufacturer contact geometry.


## Required scenarios, with evidence and extensions separated

### Advanced Driving Base

Required full interaction: differential-drive obstacle course, independent supported front/rear tool-output rotations and two ground-color inputs. Use two Large Motors for propulsion and two Medium Motors for the unloaded outputs; no dozer, lift arm, gripper, distance sensor or optional mission accessories are installed. The [research](../research/advanced-driving-base.md) fixes A left drive/E right drive, D front output/C rear output, B/F color sensors. The course, obstacle response and ground test patches are explicitly **RoboBuild simulation extensions**, not manufacturer-validated autonomous navigation. Collision stops may use disclosed simple geometric course rules; no invented range sensor or strafing. Required inputs: left/right or throttle/turn, both output controls, reset and color-signal display. Wheel radius/contact/track and source-to-scene registration remain calibration prerequisites.

### Robot Hand / Pass the Brick

Required interaction: open, grasp, hold, move/pass a sample in a scripted support path, and release using the one powered F coordinate and coupled passive linkage. No independent fingers or installed Force Sensor. The [lesson research](../research/robotic-hand.md) preserves prose left/right-button control versus SVG start clockwise 0.2 s, left pressed −100% power, left released clockwise 0.2 s. Offer those as distinct source references; do not label them identical. Duration/power are not jaw endpoints. Grasp/hold/release uses disclosed capture geometry and a modeled sample if its composition is independently authored; the lesson's six loose scoring bricks have no complete sourced BOM. Missing pivot coordinates, closed-loop branch, collision-free range and aperture remain prerequisites for a credible interaction, not grounds to substitute a five-finger hand.

### Quality Check Robot / Place Your Order

Required interaction: the combined Idea Detector + Robot Head, color presentation event, two-coordinate expressive response, eye-light feedback and reset. The [research](../research/quality-check.md) documents Color D, Distance C, motors A/F with physical-axis mapping unresolved. Main example initializes both at 75% and position 0, with eye/display actions. The possible-solution violet input uses A clockwise30/counterclockwise60/clockwise60/counterclockwise30 degrees. A separate teacher example uses red A/green F, 50% and position350. Keep these variants identifiable, not one fabricated truth table. Colors and motion are source-specific; automatic accept/reject, defect detection or additional inspection semantics are **RoboBuild extensions**. No conveyor or automatic grasp is installed. Do not bind A/F to named physical axes until checked.

### Package Sorter / Automate It — index2019

Required interaction: complete two-side pickup, fork lift to color check, accepted-package bin placement, other-package drop/shake, and return, using base yaw A, coupled fork lift F and Color D. The real mechanism has no conveyor, independent claw or extra powered carriage. The [source program](../research/package-sorter.md#documented-sorting-sequence-versus-extension) SVG begins `A0 → F240 → A90 → F25 → check → A0 → F240 → A270 → F25 → check → F240 → A0`, with A/F at25%. Check: F235, wait4s, magenta follows A0/F25/feedback/F240; otherwise feedback/F25 then three −100/+100-degree shakes at100%, restoring25%. Python uses250°/s and1000°/s shake, ending A0 then F240 rather than the SVG's F240 then A0. Preserve source variants and wrapped encoder semantics, never treat F25/F240 as stop bounds. Packages contain separate z36 gear bases; the sorter's z28 component is not their drive transmission. Kinematic capture/drop assumptions are labeled; arbitrary continuous multi-bin factory operation would be an extension. The full object cycle remains required even while linkage/contact registration is incomplete.

## Required implementation evidence

Exercise joint zero/sign composition, source-to-modeled unit conversion, limits classifications, nonlinear linkage residual/branch, differential straight/turn/reverse tracks, same-time random seeks, object attach/release boundaries and reset. Compare source-specific programs without conflating variants. Capture each complete model's actual post-assembly scenario, hierarchy identity and disclosed limitations. Calibrated physics claims additionally require measured masses/inertias, friction/contact, payload, cable clearances, sensor behavior and representative physical validation. No implementation checks or physical validation are claimed by this document.
